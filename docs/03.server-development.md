# 服务部署

上一篇：[02-Sherpa-onnx 本地模型](02.sherpa-models.md)<br />

本文部署两个示例程序：
- `XiaoZhi.Net.Sample.Server` 提供语音会话 WebSocket.
- `XiaoZhi.Net.Sample.OTA.Server` 向设备返回服务连接地址。
 
配置字段见[配置文件参考](00.configuration-file.md)，本地模型及下载工具见[模型文档](02.sherpa-models.md)。

## 一、选择部署方式

| 方式 | 前置条件 | 平台 | 适用场景 |
| --- | --- | --- | --- |
| Release 包直接运行 | 对应平台运行包、模型和配置；无需安装 .NET | Windows、Linux、macOS 的 x64 / ARM64 | 希望快速使用示例服务 |
| Release 包 Docker | Linux x64 运行包、sh、Docker Compose | Linux x64 Docker 引擎 | 希望使用容器，避免源码编译 |
| 源码发布后运行 | .NET 8 SDK、对应平台 FFmpeg 动态库及发布工具 | 上述六个平台 | 需要修改示例代码或 Function Tool |
| 源码 Docker | 仓库源码、sh、Docker Compose | Linux x64 Docker 引擎 | 希望从源码构建并管理容器 |



## 二、公共准备

### 两个服务与连接地址

| 服务 | 默认监听 | 设备使用的地址 |
| --- | --- | --- |
| 主服务 | `0.0.0.0:4530` | `ws://<设备能访问的服务器地址>:4530/xiaozhi/v1/` |
| OTA 示例 | `0.0.0.0:4531` | `http://<设备能访问的服务器地址>:4531/xiaozhi/ota` |

例如服务器局域网 IP 为 `192.168.1.100`，设备 OTA 地址填写 `http://192.168.1.100:4531/xiaozhi/ota`，OTA 返回的 WebSocket 地址应为 `ws://192.168.1.100:4530/xiaozhi/v1/`。

> [!NOTE]
> WebSocket 的客户端也可以直接连接主服务。

监听地址 `0.0.0.0` 不能填写为设备连接地址；设备上的 `127.0.0.1` 指向设备本身。请放行对应主机端口，保证设备与服务器网络互通。

> [!WARNING]
> 当前OTA 服务的 `/api/config` 接口只提供连接信息、时间信息和示例配置接口，没有固件下载地址，仅作为示例。

### 配置文件

配置文件你需要将 `config.json`、`config_*.json` 和 `config.<环境名>.json` 放在同一个目录，主服务启动时会按顺序加载。在外部目录填写自己的配置后，使用 `--config <文件路径>` 启动。

程序只接受 `--config` 与一个文件路径，缺少文件或参数错误时会报错。

主服务配置加载顺序为：

1. `--config` 指定的主配置文件；未指定时为 `Configs/config.json`。
2. 主配置文件所在目录的所有 `config_*.json`，按文件名排序，忽略大小写；主配置文件不会重复作为分片加载。
3. 可选的 `config.<环境名>.json`，覆盖前面的同名字段。

OTA 使用 `ASPNETCORE_ENVIRONMENT`，通过 `XiaoZhi__ConfigDirectory` 指向主服务的 `Configs`，通过 `XiaoZhi__Websocket__Url` 指定设备能够访问的连接地址；也可以修改其 `appsettings.json`。两个服务使用同样的环境名称，才能读取同一份环境配置。

### 下载 FFmpeg

从 [Resources Release](https://github.com/mm7h/XiaoZhi.Net/releases#release-resources) 自行下载与运行包 RID 对应的 FFmpeg 7.1 动态库包。将动态库直接放入 `server/ffmpeg`，建议保留资源包附带的 License 文件。

| 平台 | 必需动态库 |
| --- | --- |
| Windows | `avcodec-61.dll`、`avformat-61.dll`、`avutil-59.dll`、`swresample-5.dll` |
| Linux | `libavcodec.so.61`、`libavformat.so.61`、`libavutil.so.59`、`libswresample.so.5` |
| macOS | `libavcodec.61.dylib`、`libavformat.61.dylib`、`libavutil.59.dylib`、`libswresample.5.dylib` |

### 下载模型

如果需要使用本地 Sherpa 模型，请按照在 [Sherpa 模型的说明文档](02.sherpa-models.md) 中下载所需的模型文件，并放置在 `server/models` 下对应的子目录中。

### 使用本地 Docker

> [!IMPORTANT]
> 即使 Docker Desktop 在 Windows 上运行，也应下载 Linux x64 包。

在准备好配置文件、模型文件（可选，但至少需要 `Vad` 模型）和 `server/ffmpeg` 中的 Linux x64 动态库，从运行包根目录执行（将 IP 替换为设备能访问的服务器地址）：

```sh
runtime="$HOME/xiaozhi-runtime"
sh ./docker/deploy.sh --mode release \
    --package-directory "$PWD" --resource-source "$PWD/server" \
    --runtime-directory "$runtime" --public-host 192.168.1.100
```

如果已有 `config.Production.json`，sh 入口保留它，不修改其中的字段；请确认其 `WebSocketServerOption` 为 `IP: "0.0.0.0"`、`Port: 4530`、`Path: "/xiaozhi/v1/"`。配置分片合并和 JSON 校验由服务端负责，启动失败可查看容器日志。

首次导入后，实际配置位于 `$runtime/Configs`，修改运行包原来的 `server/Configs` 不会自动同步。已有 `$runtime/Configs/config.json` 时，脚本保留现有资源，不再次导入；不完整的导入目录会明确报错。

需要自定义宿主机端口时，在首次部署命令中增加：

```sh
sh ./docker/deploy.sh --mode release \
    --package-directory "$PWD" --resource-source "$PWD/server" \
    --runtime-directory "$runtime" --public-host 192.168.1.100 \
    --ws-port 14530 --ota-port 14531
```

此时设备 OTA 地址使用 `14531`，返回的 WebSocket 地址使用 `14530`；容器内部仍必须监听 `0.0.0.0:4530/xiaozhi/v1/`，不要把容器配置端口改成宿主机端口。

## 四、源码部署

### 获取源码与选择发布配置

安装 .NET 8 SDK 和 Git；使用 Visual Studio 时，安装支持 .NET 8 的 Visual Studio 2022。检出准备部署的版本：

```bash
git clone https://github.com/mm7h/XiaoZhi.Net.git
cd XiaoZhi.Net
git checkout <版本-tag>
```

发布配置位于 `demo/XiaoZhi.Net.Sample.Server/Properties/PublishProfiles`，且对各个平台的发布产物都设置成了输出一个自包含可执行文件。

Linux 发布前安装 `patchelf`；macOS 安装 Xcode Command Line Tools（`xcode-select --install`），用于处理 Sherpa 原生库的依赖路径。这些推理库是编译依赖，发布时不需要模型文件。

> [!IMPORTANT]
> 推荐在目标操作系统和架构上发布；从 Windows 发布 Linux/macOS 程序，需要另行提供在目标系统准备的 `SherpaNativeLibrariesPath`。

### 方式一：Visual Studio 发布

1. 打开 `XiaoZhi.Net.sln`，右键 `XiaoZhi.Net.Sample.Server` 项目，选择“发布”。
2. 选择已有的配置，例如 Windows x64 使用 `WinX64`；不要重新创建文件夹发布配置。
3. 保留配置中的 `Release`、目标运行时、自包含和单文件设置。FFmpeg 作为外部依赖，不打包进单文件程序；部署时按第二节将对应平台的动态库放入 `server/ffmpeg`。

4. 点击“发布”。默认输出目录为主服务项目下的 `bin/Release/net8.0/publish/<RID>/`，包含可执行文件与 `Configs`；也可将发布目标位置改为仓库下的 `artifacts/publish/<RID>/server`。
5. OTA 示例目前没有独立的发布配置，可按下方命令行方式引用同一份 `.pubxml`，输出到对应的 `ota` 目录，无需新增重复配置。

### 方式二：dotnet publish 发布

在仓库根目录执行。以下 Windows x64 示例可在 Windows 自带的 PowerShell 中运行，不要求 PowerShell 7：

```powershell
$profile = 'WinX64'
$rid = 'win-x64'
$profilePath = (Resolve-Path "./demo/XiaoZhi.Net.Sample.Server/Properties/PublishProfiles/$profile.pubxml").Path
$package = "./artifacts/publish/$rid"

dotnet publish ./demo/XiaoZhi.Net.Sample.Server/XiaoZhi.Net.Sample.Server.csproj -c Release `
    "-p:PublishProfile=$profile" -o "$package/server"
if ($LASTEXITCODE -ne 0) { throw '主服务发布失败' }

dotnet publish ./demo/XiaoZhi.Net.Sample.OTA.Server/XiaoZhi.Net.Sample.OTA.Server.csproj -c Release `
    "-p:PublishProfile=$profile" "-p:PublishProfileFullPath=$profilePath" -o "$package/ota"
if ($LASTEXITCODE -ne 0) { throw 'OTA 服务发布失败' }
```

Linux x64 示例使用 sh；其他平台替换 `profile` 和 `rid`，并满足对应平台的发布前置条件：

```sh
set -e
profile=LinuxX64
rid=linux-x64
profile_path="$PWD/demo/XiaoZhi.Net.Sample.Server/Properties/PublishProfiles/$profile.pubxml"
package="$PWD/artifacts/publish/$rid"

dotnet publish ./demo/XiaoZhi.Net.Sample.Server/XiaoZhi.Net.Sample.Server.csproj -c Release \
    -p:PublishProfile="$profile" -o "$package/server"

dotnet publish ./demo/XiaoZhi.Net.Sample.OTA.Server/XiaoZhi.Net.Sample.OTA.Server.csproj -c Release \
    -p:PublishProfile="$profile" -p:PublishProfileFullPath="$profile_path" -o "$package/ota"
```

主服务按配置名称加载现有 PublishProfile；OTA 通过 `PublishProfileFullPath` 引用同一文件，从而复用其目标平台和单文件设置。`-o` 只调整输出位置，不需要重复传入 `PublishSingleFile`、`SelfContained` 等选项。

### 准备资源并直接运行

将两个服务的发布结果整理为以下结构；通过上述命令发布时，`server` 与 `ota` 已分别生成：

```text
artifacts/publish/<RID>/
├── server/
│   ├── XiaoZhi.Net.Sample.Server[.exe]
│   ├── Configs/                    # 原有 JSON 与 assets，随项目发布
│   ├── models/                     # 自行创建并下载模型
│   ├── ffmpeg/                     # 自行创建并下载对应平台动态库
│   ├── musics/                     # 自行创建，可为空
│   ├── data/                       # 自行创建，用于运行数据
│   └── logs/                       # 自行创建，用于日志
└── ota/
    ├── XiaoZhi.Net.Sample.OTA.Server[.exe]
    └── appsettings.json
```

按第二节准备外部配置、FFmpeg 和模型，保留 `Configs/assets`。项目会将现有 `config*.json` 复制到发布目录；建议将这些 JSON 复制到运行包之外的目录，再填写 Key 和密钥，启动时使用 `--config` 指向它。不要将个人凭据写入准备公开分享的发布产物。

从发布目录的 `server` 和 `ota` 分别启动两个程序，命令与第三节的 Windows 或 Linux/macOS 直接运行方式相同。无需重新编译；将整理好的目录压缩后即可搬到相同平台和架构的机器上部署。

### 将已发布程序部署到 Docker

Docker 使用前面发布得到的 `linux-x64` 程序。在 Linux 上完成 `LinuxX64` 发布后，从仓库根目录补齐运行包的 Docker 文件和架构信息：

```sh
package="$PWD/artifacts/publish/linux-x64"
mkdir -p "$package/docker" "$package/server/models" "$package/server/ffmpeg" \
    "$package/server/musics" "$package/server/data" "$package/server/logs"
cp ./docker/deploy.sh ./docker/compose.yaml ./docker/Dockerfile.release \
    ./docker/Dockerfile.release.dockerignore "$package/docker/"
cp ./LICENSE "$package/"
printf '%s\n' '{"Version":"local","RuntimeIdentifier":"linux-x64"}' > "$package/package.json"
```

`package.json` 是部署脚本识别运行包架构的元数据，不是新的服务端配置。然后按第二节填写配置、下载模型并将 Linux x64 FFmpeg 动态库放到 `$package/server/ffmpeg`。准备完成后执行：

```sh
sh "$package/docker/deploy.sh" --mode release \
    --package-directory "$package" --resource-source "$package/server" \
    --runtime-directory "$HOME/xiaozhi-runtime" --public-host 192.168.1.100
```

此处虽然使用 `release` 部署模式，程序来自用户自己的源码发布结果，不要求下载 GitHub Release 包。Docker 只安装系统依赖并复制已经发布好的程序和 FFmpeg 动态库，不再执行 `dotnet publish` 或编译 FFmpeg；资源导入、端口设置与维护命令均与第三节的 Release 包 Docker 一致。



## 五、检查与维护

### Docker 管理命令

使用首次部署时的同一个运行目录；示例假设当前在仓库根目录或解压包根目录：

```sh
runtime="$HOME/xiaozhi-runtime"
sh ./docker/deploy.sh status --runtime-directory "$runtime"
sh ./docker/deploy.sh logs --runtime-directory "$runtime"
sh ./docker/deploy.sh check --runtime-directory "$runtime"
sh ./docker/deploy.sh down --runtime-directory "$runtime"
sh ./docker/deploy.sh up --runtime-directory "$runtime"
```

`logs` 持续跟随日志，按 `Ctrl+C` 退出。模式、构建目录、公共主机地址、端口和项目名保存到 `$runtime/deployment.env`，后续命令自动复用；这里只记录部署参数，模型密钥仍在原有 JSON 中。首次部署必须提供 `--public-host`，只填写 IPv4 或域名，不带协议、端口或路径。`up` 会构建镜像并启动或重建容器；配置修改后用 `up` 重新启动。

原 `deploy.ps1` 入口仍可用，其参数保存在 `deployment.json`。两种入口不自动转换部署记录，已有 PowerShell 部署建议继续使用原入口；切换到 sh 时首次需明确传入原运行目录、模式、运行包路径、公共地址、端口和项目名，确保复用原来的资源与数据卷。

`Configs`、`models`、`musics` 以只读目录挂载到容器，`data` 和 `logs` 使用 Compose 命名卷，容器以非 root 用户运行。单文件原生库解压目录可写且与持久化数据分开。`Down` 不删除数据卷；保留相同 `ProjectName` 才能复用原数据卷。

sh 入口的 `check` 确认两个容器正在运行且健康；Compose 健康检查覆盖主服务监听端口和 OTA `/health`。它不检查 OTA 返回地址、共享配置接口或 WebSocket 升级连接，这些可按下一节手动检查。原 PowerShell 入口的 `Check` 还会检查这些接口；两种方式都不测试设备 `hello` 完整初始化或完整语音对话。

### 原生部署检查

```powershell
Invoke-RestMethod http://127.0.0.1:4531/health
$ota = Invoke-RestMethod http://127.0.0.1:4531/xiaozhi/ota -Method Post -ContentType application/json -Body '{}'
$ota.websocket.url
```

Linux/macOS 也可用 `curl http://127.0.0.1:4531/health` 和 `curl -X POST -H 'Content-Type: application/json' -d '{}' http://127.0.0.1:4531/xiaozhi/ota`。不要将 `/api/config` 的完整响应用于公开日志或截图，其中可能包含已经填写的凭据。

看到 `status: ok` 后，确认返回地址能从设备访问；再用设备发起一次语音对话，验证录音、转写、模型回复和语音播放。服务监听成功本身不能证明云服务账号、模型权限、音色和网络可用。

### 升级

- 原生部署：停止两个服务，将新包解压到新目录，继续用 `--config` 指向原来的外部配置；迁移模型、对应平台的 FFmpeg、提示音资源、音乐、`data` 和日志，对照新模板补齐必要配置后启动。数据库路径随程序目录变化，仅保留旧工作目录不足以迁移会话记忆。
- Release Docker：下载新 `linux-x64` 包，并准备新包 `server/ffmpeg` 中的动态库。从新包根目录执行 `up`，显式传入新 `--package-directory`，继续使用原来的 `--runtime-directory` 和项目名。不要直接用新包默认的运行目录，否则无法复用原配置。
- 源码 Docker：更新到目标版本后，继续使用原运行目录和项目名执行 `up`。已有资源不会再次从 `--resource-source` 导入，新增模型需要放入实际运行目录。

### 常见问题

| 现象 | 检查内容 |
| --- | --- |
| 找不到配置文件 | `--config` 文件路径是否正确；无参数启动时是否存在工作目录下的 `Configs/config.json`；Docker 是否使用正确的运行目录 |
| 模型不存在或 ONNX 加载失败 | 实际工作目录下的文件、模型格式、架构和系统依赖；尤其是全局 `silero-native` 模型 |
| FFmpeg 不可用 | 是否使用正确 RID；动态库版本和依赖是否匹配；自行发布时不能只提供 FFmpeg 可执行文件 |
| 解压后程序不能执行 | Unix 执行权限、CPU 架构及 macOS 首次运行授权 |
| 设备无法连接 | 公共主机地址、防火墙、宿主机端口及 `/xiaozhi/v1/` 路径；不要填写 `0.0.0.0` 或设备自己的 localhost |
| 修改配置没有生效 | 修改实际运行目录中的配置；检查环境覆盖文件并重启服务 |
| Docker 导入目录不完整 | 检查暂存导入目录与缺失资源；补齐现有目录或选择新的运行目录，脚本不会强行覆盖 |
| Docker 健康但对话失败 | 检查完整 hello 初始化、云模型凭据、权限、网络及设备音频参数 |

## 六、维护者发布运行包

GitHub Actions 仅承担编译、打包和上传。入口是 `.github/workflows/release.yml`，调用 `.github/workflows/scripts/Publish-Release.ps1`：

1. 检出版本 tag，安装 .NET 8 SDK；Linux 安装单文件原生库处理所需的 `patchelf`。
2. 在六个平台的 runner 上发布主服务与 OTA，各生成一个自包含单文件程序。
3. 复制示例配置、提示音、部署文档和用户可用的模型下载工具，保留空的 `models`、`ffmpeg`、`musics`、`data`、`logs` 目录。
4. 生成 `XiaoZhi.Net-<版本>-<RID>.zip` 和 SHA256。
5. 全部编译打包成功后，将六个平台 ZIP 与 `SHA256SUMS` 上传到对应 GitHub Release。

工作流不下载 FFmpeg 或模型，不启动服务，不执行设备连接、模型推理或 Docker 部署验证。NuGet 中的 Sherpa / ONNX 推理库仍属于程序的编译依赖，单文件发布时需要处理其原生库路径；这不需要任何模型文件。

手动运行 **Release packages** 并填写版本 tag 时，仅生成 Actions 构建产物，不上传 Release。发布该 tag 的 GitHub Release 时自动上传运行包；重新运行会更新同名生成资产。`resources` Release 不触发程序打包。

Windows ARM64、Linux ARM64 和 macOS Intel 使用对应 GitHub 托管 runner，仓库须具有这些 runner 的使用资格。编译打包成功不代表所有平台已经完成实际运行验证；用户按第五节检查部署和语音对话。

FFmpeg 资源独立放在 [resources Release](https://github.com/mm7h/XiaoZhi.Net/releases#release-resources)，供用户按 RID 下载。资源是否上传不会影响程序的编译打包，不再需要 `release/ffmpeg.json` 清单。用户部署时按第二节准备 FFmpeg、模型及配置。

根目录 `scripts` 中的模型下载入口和清单用于用户手动准备模型；它们随 ZIP 分发，但不会在 GitHub Actions 中执行。`docker/deploy.sh` 与 `docker/deploy.ps1` 用于用户部署，不在发布 job 中调用。
